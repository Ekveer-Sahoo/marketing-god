# Hooks

A hook has one job: stop the scroll and earn the next second. Priority order for any piece: (1) get attention, (2) tell them what to do,
(3) everything else. So the hook is written first, before the script.

Status of this skill: rules come from `curriculum/01-hooks.md` (about 85 marketing reels studied). They have not yet been through the lab.
When a rule here conflicts with real performance data the user has, the data wins; say so in one line and suggest logging it in the lab
(don't write lab files unless asked).

## Two modes
- **Write**: the user wants hooks for a product, topic or script → follow "Writing hooks".
- **Score**: the user gives one or more existing hooks → follow "Scoring" and return a diagnosis and rewrites. Do not generate a fresh batch
  unless asked.

## Writing hooks

### 1. Get the inputs (ask only for what's missing, one short message)
- **What** is being sold or said, and the one outcome it gives.
- **Who** it is for: a specific person in a specific situation. When the buyer and the user differ (parent and child, gift giver and
  receiver, manager and team), write to the **buyer** unless the research says the user drives the purchase, and say which you chose.
- **Where** it runs (reel, paid ad, LinkedIn post, email…) and **the goal** (reach, followers, comments, saves, leads, sales).
- **Proof** available: numbers, results, demos, a recognisable name. Never invent proof.

Then look for audience research: the `audience.md` file the `audience-research` skill writes (usually `marketing/<product-slug>/audience.md`
or `lab/products/<slug>-audience.md`), or notes in the conversation. When it exists, start from its top three problems or objections, angles and
verbatim phrases, and prefer lines tagged `[own]` over `[inferred]` or `[assumed]`. Also read its **Seller facts** and **Unknown**
list: a hook must never claim something listed as unknown (a certificate, a delivery date, "no soldering"); use a placeholder and flag it.
If the file carries a draft notice, tell the user in one line that the hooks rest on provisional research. It covers their problems,
frustrations, desired outcomes, repeated questions, mistakes, objections, and the phrases they use. If there is none, write a quick version
yourself (two or three per category, marked as assumptions) and show it in three short lines before the hooks, asking the user to correct
anything wrong. Hooks written without this come out generic, which is the most common failure.

If an input is ambiguous in a way a hook would lean on ("ships in 5 days": dispatched or delivered? "real metal": solid or plated?), use
the safer reading in the hook and flag it in one line. A hook must not overstate what the product is made of or does.

### 1b. Let the goal shape the hook
| Goal | The hook should | Avoid |
|---|---|---|
| Sales / DMs / leads | Show the product or result and the buyer's situation; price or offer can be in the hook | Quiz and debate hooks that pull comments from non-buyers |
| Reach | Be broad and visual; curiosity or surprise anyone gets | Niche jargon, price |
| Comments | Ask or imply a question with an easy answer; controversy with substance | Closed statements |
| Saves | Promise a list, steps or settings worth coming back to | One-off entertainment |
| Shares | Name a person the viewer knows ("send this to the friend who…") | Hooks only about the viewer |
| Followers | Promise a series or an ongoing story | One-and-done tips |

Whenever there is something to show (a physical product, or a service or event with footage of it happening or of the result), lead with
the show-it types in `references/hook-types.md`; most of the swipe templates were written for creators and coaches and fit these badly.

Research built from pre-sale enquiries is mostly objections. Don't let the whole batch become objection-handling: at least two of the top
five should lead with the desire or the result, not a doubt.

### 2. Generate wide, then cut
Draft at least 15 candidates privately, spread across at least six different types from `references/hook-types.md` (the framing devices
there count as types). Use `references/swipe-templates.md` for sentence shapes only where one fits naturally; never force a template.
Use the audience's own words. Variety matters more than polish at this stage, because the best hook
usually comes from a type the user would not have tried.

For video, every hook has three layers that run together; write all three:
- **Visual**: what moves or looks odd in frame one (works with sound off).
- **Text on screen**: one line readable in under a second.
- **Spoken**: the first sentence.

For text formats (posts, emails, headlines) write the line only, plus the second line it sets up.

### 3. Score and cut
Score every candidate with `references/scoring.md`. Drop anything under 8/12 or with a fatal flag. Rewrite near-misses once, then drop
them if they still fail. Scores bunch together when the footage is good, so then **rank**: order the survivors by which you would bet
money on with this buyer, and keep five that differ in type.

### 4. Deliver
Give the **top 5**, strongest first, in this shape:

```
1. [type] — score /12
   Visual: …
   Text:   …
   Says:   …
   Why it should work: one line (the trigger it pulls, in plain words)
   Sets up: what the next 5 seconds must deliver for the hook to be honest
```

Show only the total in write mode; give the per-criterion line if the user asks why. Then one line: which two to test against each other
first and why (pick two that differ in type, not two versions of one idea). Offer the remaining candidates only if asked. No long preamble.

## Scoring (when the user brings a hook)
1. If the format isn't stated, assume the most likely one from context, say which you assumed, and score "works muted" on that basis
   (a bare spoken line for video with no visual described scores 0 there).
2. Score it with `references/scoring.md`; show the per-criterion marks in one compact line.
3. Name what's wrong using the failure tags there, in plain language.
4. Give three rewrites that fix the named problems, each a different type. For video, each rewrite is the spoken line plus a one-phrase
   visual. If an audience file exists, use it (it's how you judge `wrong-audience-words`). Prefer rewrites that add something new over
   repeating hooks already delivered in this conversation.
5. If it scores 10+ say so plainly and don't rewrite it for the sake of it.

## Rules that hold in both modes
- **Specific beats clever.** A number, a named situation or a concrete object. Cut empty intensifiers (huge, insane, game-changing),
  and swap claim words (fast, trusted, durable, premium) for the proof behind them; the swap table is in `references/hook-types.md`.
- **For the viewer, not about the brand or the news.** "Anthropic just announced…" got 37 likes; lines that named the viewer's situation,
  or showed something they want happening, got 100k+.
- **Open a loop the piece really closes.** If the content can't pay off the promise, change the hook, not the truth.
- **No banned openers.** The single list is in `references/scoring.md`; a banned opener is always rewritten, never delivered.
- **Not swappable.** If a competitor could run the same line unchanged, it isn't finished.
- **Negative and controversial hooks need a real insight behind them.** Otherwise they read as rage-bait and cost trust.
- **Match the language of the person the piece addresses** (the buyer, usually), including Hinglish or regional phrasing when that's how
  *they* talk. One message in another register isn't a reason to switch.
- **A customer's real message used as on-screen proof needs their permission.** Say so when you propose one, and attribute it without
  identifying them ("parent, last batch").
- **No invented numbers, results, testimonials or credentials.** Use placeholders like [X orders] and say what proof is needed.
- **Borrowed-clip hooks** (stitch, anticipation clip, "ad break") are in `references/hook-types.md`; suggest them only with footage the
  user has the right to use.
